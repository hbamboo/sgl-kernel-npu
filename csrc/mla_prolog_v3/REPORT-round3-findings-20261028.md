# 第三轮实验：两个新发现（2026-10-28）

> 承接 `REPORT-1ms-feasibility-20261028.md`。本轮**没有达成 1 ms**，但实验推翻了上一轮的
> 一个关键判断，并把真正的阻塞点定位到了源码级的确定位置。
> 代码零改动（实验旋钮已完整回退，工作树与 `02940d5` 一致）。

## 发现一（重要，纠正上一轮结论）：HBM 不是瓶颈，L2 命中率 95.9%

上一轮我写"8 passes × 324 MB = 2.59 GB 权重流量，按 3.27 TB/s ≈ 793 µs"，并据此判断
权重流量是主因。**这个算法是错的**——它假设每个核的读取都打到 HBM。

本轮用 `msprof op --aic-metrics=L2Cache` 实测（T=30456，split-M）：

```
aic_read_close_hit  = 1,111,638
aic_read_close_miss =     9,835
aic_read_far_hit    =     7,131
aic_read_far_miss   =     9,680
aic_read_hit_rate   = 95.93 %      <-- 第二轮 93.88%，稳定
```

**L2 读取命中率 95.9%**：32 个核读同一份 10.12 MB 权重，绝大部分命中 L2，
真正落到 HBM 的只有约 4%。

这有两个后果：

1. 上一轮"权重重复搬运 = 2.59 GB HBM 流量"的估算作废，HBM 远没有被打满；
2. 真正的瓶颈是**每核 MTE2 把数据从 L2 填进 L1 的速率**，实测每核约 6.7 GB/s
   （10.12 MB / 1585 µs）。这是 L1 填充带宽，不是 HBM 带宽。

所以"减少核数省 HBM 带宽"这条路从一开始就不成立——实测也确实更差（8/16/24 核 →
7916/4177/2927 µs）。

## 发现二：step 的硬阻塞不是 L0 尺寸，是向量段每核 token 循环

上一轮我判断"1 ms 需要 step 512，被 32 KB L0A 卡死"，并按这个思路做了实验：
本轮重新接上 `MLA_PROLOG_V3_MM_BASEK` / `MM_BASEN` 两个旋钮，把 **mm1 / mm2 / mm3 / mmQn
四处**的 `baseK` 与 `baseN` 一起调到最小（上一轮只调了 baseK，漏了 mmQn 的 baseN——这次补齐了）：

| baseK | baseN | step | L0A 需求 | L0C 需求 | 结果 |
|---|---|---|---|---|---|
| 256 | 128 | 256 | 64 KB（超）| 128 KB（超）| 越界 |
| 128 | 64 | 256 | 32 KB（卡满）| 64 KB（卡满）| **仍越界** |
| 128 | 32 | 256 | 32 KB | 32 KB | **仍越界** |
| 64 | 32 | 256 | 16 KB | 32 KB | **仍越界** |
| 128 | 64 | 192 | 24 KB | 48 KB | **仍越界** |

把 L0 深度压到远低于上限仍然全部越界 ⇒ **限制根本不在 L0**。

根因在向量段，与 cube 无关：

```
每个 AIV 核要处理的 token 数 = ceil(step / 64 AIV 核)
  step=128 -> 2 个   (当前唯一可用)
  step=192 -> 3 个   -> 崩
  step=256 -> 4 个   -> 崩
```

这条约束在 `PERF-COUNTEREVIDENCE.md` §1c3 里已被记录过（"`ceil(step/64 AIV 核) ≤ 2`
是向量段逐 token 的 UB/offset 组织方式所致，不是容量问题，因为 UB 预算自洽"），
本轮我按 L0 的思路重新追了一遍，实测再次确认：**与 L0 无关**。

## 结论

| 项 | 状态 |
|---|---|
| decode | 无劣化（T=1 41.5 µs、47 层 1139 µs，噪声内）|
| prefill | 2348 µs，未回退 |
| 1 ms | **未达成**，但阻塞点已从"L0A 尺寸"修正为"向量段每核 token 循环" |
| 验收 | 27/27（上一轮同一棵树）|

### 这修正了 1 ms 的施工方向

上一轮 `DESIGN-kernel-rewrite.md` 的方向仍然成立，但**着力点要换**：

- 不是"压缩 L0 tile 深度让 step 变大"——实测无效，L0 根本不是瓶颈；
- 而是"**重写向量段，让每个 AIV 核能循环处理 >2 个 token**"。这是让 step 超过 128 的
  唯一前提；step 一旦到 512，passes 从 8 降到 2，按发现一（L2 命中）的真实瓶颈模型，
  MTE2 部分约 1585 → 396 µs，叠加 cube 754 µs，总量有望进入 0.8–1.0 ms。

具体改动位置（已定位，未实施）：`kernel_mla_prolog_split_m.h` 的 `AivProcess` 与
`RmsNormCq` / `RmsNormRopeScatterCkvKr` / `DequantQcAndRopeQc` 里的逐 token 循环，
以及 `curVecTokenMax_` 驱动的 `sincosBuffer_` / `shareBuffer_` 分区（第 547–568 行）。
关键在于让这些缓冲区按"每核 1 token"分配、外层再套一层 token 循环，而不是一次性按
`step/64` 个 token 预留。

### 需要明确的风险

改向量段会动 AIC/AIV 的 barrier 结构，本轮已见到两次 507015（设备级异常，会打断同卡
其他租户）。建议在独占卡上做，且先只支持 `weight_quant_mode=3` 一种组合、保留旧路径做门控。
