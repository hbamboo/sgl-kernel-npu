# 第 ③ 条（利用率达理论上限）的反证链

本文件把"为什么当前 kernel 架构下达不到 roofline"的每条假设、实验设置、实测数据与结论
列全，便于逐条复核。所有实验都在同一台机器（Ascend950DT，device 5）、同一二进制上，
同一会话内 A/B 完成；机器上限实测为 HBM **3.27 TB/s**、bf16 **424 TFLOP/s**。

## 0. 当前基线

| 场景 | 实测 | roofline | 占比 |
|---|---|---|---|
| 解码 T=1 | kernel 18.2 µs（总 32.9 µs，PyBind 路径） | 5.3 µs（带宽） | **29%** |
| 预填 T=256 | kernel 66 µs | 10.4 µs（算力） | **16%** |
| 预填 T=2048 | kernel 626 µs | 83.6 µs（算力） | **13%** |

## 1b. 这台机器的测量方差（重要）

同一份二进制、同一脚本，跨窗口实测的差异可达 **±20%**：本会话里 T=256 出现过
`73.9 µs`（某次窗口）与 `89.7 µs`（多次稳定复现），T=2048 对应 `524 µs` 与 `650 µs`。
差异来自共用卡上其它租户的负载（`npu-smi` 可见各卡 4.7 GB 空闲态 ↔ 90 GB 满载态）。
**结论**：所有横向对比必须在同一窗口内交替测量；本文档中的优化结论都是在同窗口 A/B 下得出的，
但绝对数字会随窗口浮动。

## 2. 为什么 L1 是硬的（源码级）

`mla_prolog_comm_arch35.h`：

```cpp
constexpr uint32_t L1_A_SIZE = 128 * 1024;   // 且按 * 2（ping/pong）分配
constexpr uint32_t L1_B_SIZE = 128 * 1024;   // 同上
```

`kernel_mla_prolog_split_n_arch35.h`：`pipe_->InitBuffer(aBufL1_, L1_A_SIZE * 2)`、
`InitBuffer(bBufL1_, L1_B_SIZE * 2)` → 合计 **512 KB = 整块 L1**。

而每轮暂存深度 `kL1StepSize = baseK × stepK = 128 × 4 = 512`：

- B 侧：`baseN 128 × 512 × 2 B = 128 KB` —— 正好等于 `L1_B_SIZE`；
- A 侧（m=128 时）：`128 × 512 × 2 B = 128 KB` —— 正好等于 `L1_A_SIZE`。

两侧同时顶格 ⇒ 加大 `baseK`/`stepK` 必溢出（#5 实测 507015），减小只会让 L0 瓦片更浅。
解码态（m=1）A 侧近乎空闲，但 B 侧仍要满 128 KB，`kL1StepSize` 同样无法增大。

这解释了为什么 cube 只跑到 ~7%（预填 mm1+mm2）：权重必须穿过固定的 512 KB L1 与
128 KB 双缓冲，吞吐由 L1→L0 事务粒度决定，而非任何可调参数。

## 3. 结论

在**不改写 kernel 数据流**的前提下，第 ③ 条不可达。要突破只有三条路（报告第 12 节）：
A 融合 mm1+mm2（3–6%）、B 权重常驻 L1 的持久 kernel（解码 kernel 有望 18.2 → 8~10 µs）、
C 换 K 切分（预填下投影有望 −30%）。三者都需要改 kernel 并与 golden 反复回归，
其中 B/C 还需要独占卡与较长迭代窗口。
