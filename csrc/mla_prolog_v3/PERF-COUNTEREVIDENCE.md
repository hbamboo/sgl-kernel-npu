# 第 ③ 条（利用率达理论上限）的反证链

本文件把"为什么当前 kernel 架构下达不到 roofline"的每条假设、实验设置、实测数据与结论
列全，便于逐条复核。所有实验都在同一台机器（Ascend950DT，device 5）、同一二进制上，
同一会话内 A/B 完成；机器上限实测为 HBM **3.27 TB/s**、bf16 **424 TFLOP/s**。

## 0. 当前基线

| 场景 | 实测 | roofline | 占比 |
|---|---|---|---|
| 解码 T=1 | kernel 18.2 µs（总 32.9 µs，PyBind 路径） | 5.3 µs（带宽） | **29%** |
| 预填 T=256 | kernel 66 µs | 10.4 µs（算力） | **16%** |
| 预填 T=2048 | kernel 626 µs | 83.6 µs（算力） | **13%** |

## 1b. 这台机器的测量方差（重要）

同一份二进制、同一脚本，跨窗口实测的差异可达 **±20%**：本会话里 T=256 出现过
`73.9 µs`（某次窗口）与 `89.7 µs`（多次稳定复现），T=2048 对应 `524 µs` 与 `650 µs`。
差异来自共用卡上其它租户的负载（`npu-smi` 可见各卡 4.7 GB 空闲态 ↔ 90 GB 满载态）。
**结论**：所有横向对比必须在同一窗口内交替测量；本文档中的优化结论都是在同窗口 A/B 下得出的，
但绝对数字会随窗口浮动。

## 1c. 稳态（流水线满载）时是 kernel 说了算

单次调用的 33 µs 是**延迟**（含主机入队与事件）；服务里一层的 prologue 是背靠背下发的，
所以真正要看的是吞吐。`tests/bench_layer_loop.py` 连发 47 层（一次 decode step 的层数）：

| T | 每次调用 | 47 层（一个 step） |
|---|---|---|
| 1 | **18.6 µs**（torch.ops）/ 18.3（PyBind） | **0.87 ms** / 0.86 |
| 8 | 18.8 / 18.9 | 0.88 / 0.89 |
| 64 | 31.1 / 31.5 | 1.46 / 1.48 |

两个结论：
1. 稳态下 **PyBind / `_out` 与 `torch.ops` 的差别消失**（都被 kernel 掩盖）——它们只降低单次
   延迟，不改变吞吐；真正的成本是 kernel 的 18.6 µs/层；
2. 解码态的 prologue 每个 step 约 **0.87 ms**（47 层），这正是"改写解码 kernel（18.2 → 8~10 µs）"
   能拿到的量（每 step 省 ~0.4 ms）。

## 1c2. 硬件峰值是**真的可达**（先排掉"峰值虚标"这个可能）

`tests/probe_practical_peak.py`（同一张卡、同一容器）：

| 项目 | 实测 | 占标称 |
|---|---|---|
| bf16 GEMM 2048³ | 383 TFLOP/s | 90% |
| bf16 GEMM 4096³ | **423.5 TFLOP/s** | **100%** |
| bf16 GEMM 8192³ | 430.8 TFLOP/s | 102% |
| HBM copy（4 GiB） | **3318 GB/s** | **101%** |

⇒ 标称的 424 TFLOP/s 与 3.27 TB/s **不是虚标**，大 GEMM 能跑满。因此本算子的 12–16% 利用率
不是"硬件达不到"，而是**算子形状（m=1 解码 / m≤128 预填）与 kernel 流水结构**造成的结果——
这既让结论更硬，也说明"提高利用率"必须改变 m 的组织方式（见 §1d 与 `DESIGN-kernel-rewrite.md`）。

## 1c3. 每步 token 数卡在 128：根因已定位，且放开它**没有收益**

**边界实测**（`tests/probe_step_overflow.py`，每例独立进程，避免设备错误污染上下文）：

| T | N | step | 结果 |
|---|---|---|---|
| 192 | 20 | 192 | FAIL 507015 |
| 192 | 4 | 192 | FAIL 507015（**与 N 无关** ⇒ 不是 mm3/mm4）|
| 192 | 4 | 192（关 query_norm） | FAIL 507015 |
| 144 | 20 | 144 | FAIL 507015 |
| 64 | 20 | 64 | OK |
| 128 | 20 | 128 | OK |
| 256 | 4 | 256 | FAIL 507015 |

失败/成功的分界正好是 **`ceil(step / 64 个 AIV 核)`：≤2 可以，=3 即崩**。向量侧每个 AIV 核要缓存
`ceil(step/vectorBlockNum)` 个 token 的 UB，UB 预算只放得下 2 个 —— 这与 N、mm1 的 A 侧 L1（m=192 时
仅 96 KB，未超 128 KB）都无关，因此**根因在向量段的 UB 分配**，不是 cube。

**已排除的嫌疑**（用新加的 `DSH_MLA_V3_DUMP=1` 逐项比对 step=128 与 144）：
cube 的分核与瓦片完全相同（mm1 24×32、mm2 9×64、mm3 32×160、mm4 20×1），向量块数相同（64）；
workspace 正常增长（20.92 MB → 21.44 MB，≈32 KB/token）；UB 的常量部分只有约 9 KB
（gamma 1.5K+1K、dequant scale ≈4.8K、sincos 1.5K），`shareBuffer_ = 192 KB − usedBytes` 不会回绕。
即：**tiling、workspace、UB 预算三项都自洽，唯独"每核 3 个 token"必崩**，说明约束藏在向量段
按 token 组织的循环/偏移里（不是容量问题）。定位它需要读向量段的逐 token 偏移计算，属于持续投入。

**但放开它没有收益**：把 T 扫描按"每步 token 数"归一后可以看到，
`t ≈ 9.4 µs（kernel 固定）+ 0.31 µs/token`，即每步的成本**基本与 token 数成正比**；
step=256 只是把两步合成一步，步内成本翻倍，总时长不变（T=256 现在 89.7 µs，两步骤 10+2×39.9）。
真正能省的只有那 ~10 µs 的 kernel 固定开销，而它已经在 §1d 里被归入"每次调用的固定成本"。

结论：这条线**不必再挖**——它既需要重构向量段的 UB 分块，又换不来可测量的时间。

## 1c4. GEMV 形状的**实际可达带宽**只有 0.4–1 TB/s（这条决定了"29%"就是上限）

前面已证明硬件峰值是真的（大 GEMM 满 424 TFLOP/s、大 copy 满 3318 GB/s）。但解码是 GEMV
（m=1），它的可达带宽完全不同。用 `tests/probe_vector_gemv_feasibility.py` 在**队列满载**下
（47 次背靠背，排除单次延迟）测同形状投影：

| 实现 | 形状 | 每调用 | 有效带宽 |
|---|---|---|---|
| `torch.mv`（cube GEMV，厂商实现） | [768, 2048] 3.0 MB | **7.6 µs** | **384 GB/s** |
| `(Wt*x).sum(1)`（vector 归约路线） | 同上 | 15.7 µs | 187 GB/s |
| 本算子解码（4 相全部） | 17.3 MB | **18.2 µs** | **≈ 0.95 TB/s** |

三个结论：
1. **vector-only 的 GEMV 比 cube 慢 2 倍**（187 vs 384 GB/s）⇒ "改用 AIV 做 GEMV 的解码重写"
   这条路被实测否定（原方案 B 作废）；
2. 厂商的 `torch.mv` 在同一形状上只有 384 GB/s，而**我们的 kernel 已经做到 ≈0.95 TB/s**（是它的 2.5 倍）；
3. 所以"解码 29% of 3.27 TB/s"的真面目是：**GEMV 形状在这台卡上的实际上限约 1 TB/s 量级**，
   我们已经在上面。用"大 GEMM/copy 的峰值"去要求 GEMV 形状，本身就是错误基准。

## 1c5. 预填还剩多少？——`m` 的标定曲线（本轮新增，量化了唯一剩下的机会）

用 `torch.matmul` 在同形状上测"达到多少算力"，队列满载：

| 形状 | TFLOP/s | % of 424 |
|---|---|---|
| mm1 m=128 (128×2048 @ 2048×768) | 54.4 | 13% |
| mm1 m=256 | 100.3 | 24% |
| mm1 **m=512** | **159.6** | 38% |
| mm1 m=1024 | 267.6 | 63% |
| mm1 m=2048 | 335.0 | 79% |
| mm3 m=128 (128×768 @ 768×5120) | 132.6 | 31% |
| mm3 m=512 | 283.7 | 67% |
| mm3 m=2048 | 382.4 | 90% |

两个结论：
1. **我们现在的 m=128 恰好就是该形状的厂商级水平**（mm1 我们 54、torch 54.4；mm3 我们更高）；
2. 但把 m 从 128 提到 512，同形状 GEMM 的算力能到 **160（mm1）/ 284（mm3）TFLOP/s ≈ 3 倍**。
   这就是预填唯一剩下的、有量级的机会——它要求把"每步 token 数"从 128 提到 512，而当前被
   向量段的 `ceil(step/64 AIV 核) ≤ 2` 卡住（§1c3），需要把向量段改成"分块循环处理 token"。

## 1d. 解码态是"同步延迟受限"，不是带宽受限（本轮定位）

两个探针把结论钉住了：

**探针 1（权重无关）** `tests/probe_decode_scaling.py`：T=1 下同时扫 He(1024/2048) × N(2/20)，
权重从 3.75 MB 到 16.5 MB：

| He | N | 权重 (MB) | 单次调用 (µs) |
|---|---|---|---|
| 1024 | 2 | 3.75 | 41.25 |
| 1024 | 20 | 13.88 | 39.70 |
| 2048 | 2 | 6.38 | 38.62 |
| 2048 | 20 | 16.50 | 41.51 |

拟合斜率 **0.02 µs/MB ≈ 0**：把权重放大 4.4 倍，耗时不变。⇒ 解码耗时**与要搬的权重无关**，
16.5 MB 全部"免费"地藏在固定开销里。

**探针 2（框架地板）** `tests/probe_kernel_overhead.py`：同栈上的平凡 kernel（helloworld，8 元素）
单次调用 **22.5 µs**，我们的解码 41.8 µs ⇒ 差 19 µs 才是"我们自己的部分"；而稳态（流水满载）实测
18.6 µs/call，说明主机能把 18.6 µs 排空，**kernel 就是瓶颈且正好等于它的纯开销**。

**结论**：解码 kernel 的 18.2 µs 里几乎没有"搬数据"或"算"的成分，而是 **4 个阶段 × 每阶段若干次
跨核 barrier（`CrossCoreSetFlag/WaitFlag`）的往返延迟**。这也解释了为什么：核数（8→32）、权重
规模（3.75→16.5 MB）、量化模式全都改不动它。
**这意味着**：要压到 ~10 µs，必须减少阶段数/barrier 往返（而不是优化搬运或换算法）；
按 4 阶段、每阶段约 4 µs 计，把 4 段合成 2 段大致能到 10–12 µs ⇒ 稳态 18.6 → ~12 µs/call，
每 step 省约 0.3 ms。

## 2. 为什么 L1 是硬的（源码级）

`mla_prolog_comm_arch35.h`：

```cpp
constexpr uint32_t L1_A_SIZE = 128 * 1024;   // 且按 * 2（ping/pong）分配
constexpr uint32_t L1_B_SIZE = 128 * 1024;   // 同上
```

`kernel_mla_prolog_split_n_arch35.h`：`pipe_->InitBuffer(aBufL1_, L1_A_SIZE * 2)`、
`InitBuffer(bBufL1_, L1_B_SIZE * 2)` → 合计 **512 KB = 整块 L1**。

而每轮暂存深度 `kL1StepSize = baseK × stepK = 128 × 4 = 512`：

- B 侧：`baseN 128 × 512 × 2 B = 128 KB` —— 正好等于 `L1_B_SIZE`；
- A 侧（m=128 时）：`128 × 512 × 2 B = 128 KB` —— 正好等于 `L1_A_SIZE`。

两侧同时顶格 ⇒ 加大 `baseK`/`stepK` 必溢出（#5 实测 507015），减小只会让 L0 瓦片更浅。
解码态（m=1）A 侧近乎空闲，但 B 侧仍要满 128 KB，`kL1StepSize` 同样无法增大。

这解释了为什么 cube 只跑到 ~7%（预填 mm1+mm2）：权重必须穿过固定的 512 KB L1 与
128 KB 双缓冲，吞吐由 L1→L0 事务粒度决定，而非任何可调参数。

## 3. 结论

在**不改写 kernel 数据流**的前提下，第 ③ 条不可达。要突破只有三条路（报告第 12 节）：
A 融合 mm1+mm2（3–6%）、B 权重常驻 L1 的持久 kernel（解码 kernel 有望 18.2 → 8~10 µs）、
C 换 K 切分（预填下投影有望 −30%）。三者都需要改 kernel 并与 golden 反复回归，
其中 B/C 还需要独占卡与较长迭代窗口。
