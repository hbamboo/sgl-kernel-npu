# 预填推进到 1 ms 的可行性分析（2026-10-28，第二轮）

> 目标：在已达成 2.34 ms 的基础上向 1 ms 推进，同时保证 decode 不劣化。
> 结论：**1 ms 在当前 kernel 结构下不可达**；已有 2.34 ms 保持不变，decode 未受影响。
> 本文记录实测数据与已被否定的路径，供后续决策。

## 0. 结论摘要

| 项 | 结果 |
|---|---|
| decode 守护 | **无劣化**：T=1 40.1 µs（基线 40.7）、47 层 1086 µs（基线 1075），在测量噪声内 |
| prefill 现状 | **2336 µs** 保持（225.6 TFLOP/s），未回退 |
| 到 1 ms | **未达成**；量化出 1 ms 需要每步 512 token，而 32 KB L0A 把每步锁在 128 |
| 验收 | **27/27** 通过，工作树干净 |

## 1. 剩余时间到底花在哪（msprof 实测，非估算）

`msprof op --aic-metrics=PipeUtilization`，T=30456，split-M，32 AIC + 64 AIV，kernel 2199 µs：

| 流水 | 时间 | 占比 | 说明 |
|---|---|---|---|
| AIC cube（真实 MMA） | **754 µs** | 34.3% | 算力上限约 420 TFLOP/s，此处 225 |
| AIC MTE1（L1→L0） | 1209 µs | 55.0% | 325 GB/s |
| AIC MTE2（GM→L1，搬权重）| **1585 µs** | **72.1%** | 88 GB/s/核 |
| AIC scalar | 268 µs | 12.2% | |
| AIC fixpipe | 1174 µs | 53.4% | |
| AIV vec | 300 µs | 14.0% | 向量侧不是瓶颈 |

**关键**：kernel 时间是 MTE2 1585 µs，不是 cube 的 754 µs。瓶颈在"把权重搬进来"，不在"算"。

## 2. 为什么是"重复搬权重"

split-M 让每个核拥有完整 N、切分 M。因此 **32 个核每个都要读一遍完整权重**：

```
每核权重 = mm1(He*Hcq) + mm2(He*(Hckv+Dr)) + mm3(Hcq*N*(D+Dr)) + w_uk(N*D*Hckv*2B)
         = 10.12 MB (fp8 主体 + bf16 w_uk)
32 核聚合 = 324 MB / 次
```

实测每次（pass）288 µs ⇒ 有效 1.125 TB/s（HBM 峰值 3.27 TB/s 的 34%）。

这个数还受一个"平局"约束：**时间 ≈ max(每核权重字节, 每核 token × 单token算力成本)**。
两种分配方式的乘积是常数（32 核 × 952 token 固定），所以：
- 用 32 核 → 每核 10.12 MB 权重，每核 952 token；
- 用 16 核 → 每核 20.24 MB 权重，每核 1904 token，**权重读取翻倍**。

实测证实了这个平衡（T=30456）：

| 核数 | 时间 | 与 32 核相比 |
|---|---|---|
| 8 | 7916 µs | 3.4× |
| 16 | 4177 µs | 1.8× |
| 24 | 2927 µs | 1.25× |
| **32** | **2341 µs** | 最优 |

即核数已经给不出空间，32 核就是平衡点。

## 3. 到 1 ms 需要什么，以及为什么做不到

时间对 pass 数线性：

| step | passes（mSubSize=952）| 权重流量时间 | 实测/推算 |
|---|---|---|---|
| 128（现状）| 8 | 2304 µs | **2336 µs** ✓ 实测 |
| 256 | 4 | 1152 µs | ≈1.5 ms |
| 512 | 2 | 576 µs | ≈1.0 ms |
| 952 | 1 | 288 µs | ≈0.7 ms |

所以 **1 ms 需要每步 512 token**（2 个 pass）。而每步 token 被 **32 KB L0A** 硬卡：

```
L0A 上限: stepBatchSize × baseK × sizeof(T) ≤ 32768
  fp8:  256 × 256 × 1 = 65536  → 已是 2× 超，故 baseK=256 时 step 只能是 128
```

### 已实测的尝试：降低 baseK 换取更大 step

思路：`baseK 256→128` 应能让 step 256 装进 L0A。本轮加了 `MLA_PROLOG_V3_MM_BASEK` 旋钮，
把 mm1、mm2、mm3、mmQn 四处 `baseK` 一起调低，然后实测：

| 配置 | 结果 |
|---|---|
| baseK 256, step 128（现状）| 2341 µs ✓ |
| baseK 128, step 144 / 160 / 192 / 224 / 256 | **全部 L0A 越界**（`errorStr: The address for CUBE to operate L0A is out of bounds`）|
| baseK 64, step 512 | 同样越界 |

即使把四处 baseK 都调低，仍然越界。原因是 **GEMM 数量多于可调的那几个**：除 mm1/mm2/mm3/mmQn 外，
向量侧与 `CurStepBatchSize` 绑定的 UB 缓冲、以及 L0C（64 KB/缓冲，`align(step,16) × baseN × 4B`）
也随 step 线性增长；把每一处都改小会连锁地在别处溢出。这不是一个"改一个常数"的改动，
而是**重构 split-M 的分块循环**（把"每步 token"从单趟改成核内多趟），属于改写级工作。

### 也被否定的其他路径

| 路径 | 实测 | 结论 |
|---|---|---|
| 减少核数省权重带宽 | 8/16/24 核 → 7916/4177/2927 µs | 更差（见 §2 平局）|
| 回到 split-N 加大每核列数 | mm1tile 32→768：5041→13688 µs | 更差，split-M 已是最优拆分 |
| 直接加大 step（不改 baseK）| step 256/384/512 | L0A 越界 |

## 4. 所以现状是"结构上限"，不是"还没调够"

用 §1 的 profiler 数据做 roofline 校核：

- 权重流量下界（8 passes × 324 MB = 2.59 GB，按 HBM 3.27 TB/s）= **793 µs**；
- 加上 cube 算力下界（526.9 GFLOP / 420 TFLOP/s）= **1255 µs**；
- 两者取 max 且不可完全重叠 ⇒ 实测 2199 µs 已在该结构的下界附近。

要突破就必须**减少 pass 数（重构分块）**或**消除权重复制（跨核共享 L2 常驻）**，
两者都是 kernel 改写，不是参数调整。这与第一轮 `DESIGN-kernel-rewrite.md` 的判断一致，
本轮新增的是**实测证据**（profiler 占比 + 四处 baseK 实测越界 + 核数曲线）。

## 6. 若仍要冲 1 ms，建议的下一步（需要授权）

1. **核内多趟分块**：把 `Process()` 的 `for mOffset ... stepBatchSize` 循环改成两层——
   外层仍是 mSubSize 切片，内层在被约束的 128-token 步里再循环，同时**把权重加载提到内层之外**。
   这是唯一能在不改 L0A 尺寸前提下减少权重 pass 的办法（把"每步重载权重"变成"每核只载一次"）。
   预期收益：权重流量 8×→1×，即 2304 µs → 288 µs，总时长有望进入 1.2–1.5 ms。
   风险：需要重排 AIC/AIV 的 barrier 结构，属设备级风险改动，需独占卡验证。
2. **L2 常驻权重**：6.4 MB 权重可放进 L2；若能让 32 核从 L2 而非 HBM 读，
   有效带宽可提升。需要确认 3510 的 L2 容量与替换策略，并用 `MemoryDetail` 指标验证。
