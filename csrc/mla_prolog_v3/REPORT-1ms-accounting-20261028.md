# 1 ms 的定量核算与结论（2026-10-28，第 5–6 轮）

> 基线已固化为 tag `baseline-2.3ms`（commit `60ddbad`）。
> 本文记录按计划推进时的定量核算。**代码零改动**（所有实验旋钮已回退，工作树干净）。

## 1. 先纠正我自己的一处误判

`PLAN-step-loop-rewrite.md` 提的方案是"把权重常驻 L1、加载提到 step 循环外"。核算后**该方案不可实现**：

| 权重 | 大小 | L1_B（ping+pong = 256 KB）|
|---|---|---|
| mm1 B | 1.50 MB | 超 6.0× |
| mm2 B | 1.12 MB | 超 4.5× |
| mm3 B | 3.75 MB | 超 15.0× |

split-M 每核持有**完整 N**，L1_B 装不下，必须按 K 分块流式搬。所以"权重常驻"不成立。

## 2. 但"每 pass 重流权重"是真的，且是主因

`AicProcess` 每次进入把 `weightDqOffset/weightDkvKrOffset/weightUqQrOffset/weightUkOffset` 重置为 0，
而 `AicProcess` **每个 step 调用一次**。所以 B 每 step 重读一遍。

每核流量（T=30456，mSubSize=952，step=128，8 passes）：

| 项 | 每核字节 |
|---|---|
| mm1 B | 1.50 MB |
| mm2 B | 1.12 MB |
| mm3 B | 3.75 MB |
| mm4 B（w_uk, bf16）| 3.75 MB |
| **B 单次合计** | **10.12 MB** |
| B × 8 passes | **81.0 MB** |
| A（token，走全 K）| 1.86 MB（**仅占 2.2%**）|
| **合计** | **82.9 MB** |

⇒ **权重占 97.8% 的搬运量**，且每 pass 重读一次。

## 3. MTE2 是不是已经打满？——接近，但没满

msprof（device 0，T=30456）：

```
aic_time    = 2200 us      kernel wall
aic_mte2    = 1583 us  (72% of wall)   active_bw = 87.8 GB/s/核
aic_cube    =  754 us  (34%)
aic_mte1    = 1209 us  (55%)
aic_fixpipe = 1170 us  (53%)
```

- 每核 82.9 MB / 1583 µs = **52 GB/s**，约为每核 HBM 份额（101 GB/s）的 **52%**；
- 流水线时间之和 / wall = **2.27**，说明各 pipe 已在互相重叠，不是串行；
- 所以 MTE2 有约 2 倍的提升空间，但**不会到零**。

## 4. 到 1 ms 的账

设 MTE2 能跑到 101 GB/s/核（理想满带宽），cube 754 µs 与 MTE2 重叠：

| passes | B 流量 | MTE2 需求 | wall 由谁决定 |
|---|---|---|---|
| 8（现状，step 128）| 81.0 MB | **860 µs** | MTE2 → ~2.3 ms（实测，含未满带宽）|
| 4（step 256）| 40.5 MB | 430 µs | **cube 754 µs** |
| 2（step 512）| 20.3 MB | 215 µs | **cube 754 µs** |

⇒ **passes ≤ 4 时，wall 就由 cube 的 754 µs 决定，1 ms 可达。**

这纠正了我先前在草稿里写的"1 ms 物理不可达"——**1 ms 是可达的**，
前提是 step 能超过 128。

## 5. 但 step ≤ 128 是全路径硬边界（第 5 轮实测）

| 尝试 | 结果 |
|---|---|
| 减核（8/16/24）| 更差（7916/4177/2927 µs），聚合流量守恒，只少了算力 |
| 压 baseK 到 64（A tile 16 KB）| 仍崩，bf16 路径也崩 |
| 压 baseN/baseK 组合（128/64, 128/32, 64/32）| 全崩 |
| 只放大 1 个 GEMM 的 step | 仍崩 ⇒ 不是某个 GEMM 的 L0 |
| **bf16 路径 step>128** | **也崩** ⇒ 与量化、与 tile 参数无关的**全路径**限制 |
| 加大 B DMA（baseN12 64→128）| 2336 → 2325 µs（0.5%，噪声内）⇒ 不是 DMA 笔数受限 |

## 6. 结论

| 问题 | 答案 |
|---|---|
| 1 ms 可达吗？| **可达**，条件：step ≥ 256（passes ≤ 4），此时 wall 由 cube 754 µs 主导 |
| 卡在哪？| `stepBatchSize ≤ 128` 的全路径上限，**不是 L0/L1 容量、不是带宽、不是 DMA 形状** |
| 能靠调参解决吗？| **不能**，六条路径全部实测否定（见 §5）|
| 需要什么改动？| 改 `Process()` 的 step 步进本身（让一次 AIC 处理多于 128 个 token 而不越界），属重写 |

## 6b. 第 6 轮补充：L0A 是必要不充分条件

按 §7 的建议做了 bf16 二分（bf16 不含 MXFP8 scale 分支，故障应更干净），结果：

**bf16 在 step=160 也崩，同样报 L0A 越界。** 但原因与 fp8 不同：
bf16 的 、元素 2 字节，所以 A tile = ：
step=128 → 32768（正好）、step=160 → 40960（超）。**bf16 从 step 129 起必然溢出**，
这与量化无关，纯粹是 32 KB L0A 的字节算术。

于是把 fp8 的 baseK 压到 64（A tile 只有 ）：
step=256 → 16384 B，**L0A 还有 2 倍余量，但仍然崩**。

⇒ **L0A 是必要不充分条件**。存在第二个与 step 线性相关的约束，
且它也不随 baseK 缩放（否则压到 64 就该放过）。定位到的下一个嫌疑是
L0C 侧： 的 fixpipe 以  作行跨度输出
 的 C tile，L0C 64 KB/缓冲，。

**结论不变但更硬**：要放大 step，需要同时满足 L0A、L0C、L1_A 三处的字节约束，
而这三处的余量不是独立的——压一处会把另一处顶出去。这已经超出调参范围，
是要按目标 step 重新推导并分配三处 tile 尺寸的工程。

## 7. 建议的下一步（比之前更聚焦）

既然限制是"step ≤ 128"而非带宽，且 bf16 也崩，最省事的验证是把 `stepBatchSize` 设成 192
**在 bf16 路径上**看崩在哪个 pipe（bf16 不涉及 mxfp8 的 scale 分支，定位更干净）。
若确认是 A 侧的 `mSizeAligned × kL1StepSize` 与 `L0A_PP_SIZE` 的乒乓槽位冲突，
则改 `mmLocalTensors` 的槽位寻址（或让 A 复用同一个槽）即可，不必重写整个循环——
这比原计划小得多。
